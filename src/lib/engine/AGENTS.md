# Engine rules
- Run lifecycle (agent_runs) changes only through engine_transition; lifecycle.ts must mirror public.engine_stage_allowed. Why: models and clients cannot set arbitrary states.
- Events append via engine_event with per-run seq allocated atomically; clients replay with an afterSeq cursor. Store milestones only, never tokens or raw tool output. Why: reconnect without duplicates or bloated tables.
- Recorder writes are queued and best-effort; recording failures are counted, never break a run. Why: observability must not cost user work.
- Final stage comes from finalStage() facts (stop, error, blocker, step cap, pending approvals); never COMPLETED just because the model replied.
- Explicit promise-only natural finishes get one same-model tool-required follow-up within the step budget; repeated promises block completion, refusals/Stop/approval waits never continue. Why: narration is not executed work.
- Stored errors/events pass redact(); categories come from classifyError. Why: no secrets in logs.
- Model capabilities come from model-registry.ts; unknown models are flagged, not assumed capable. One fallback only, before any tool ran, for provider/rate/timeout/network errors.
- Autonomy is enforced server-side in /api/agent via autonomy.ts; "supervised"/"autonomous" keep legacy meanings. MCP non-read-only actions always need approval at every level.
- Skills: matching/always-on/dependency skills load in full; others are listed and recorded when read_skill loads them.
- Resume: a new run injects a checkpoint built from the previous unfinished run's recorded events (checkpoint.ts); engine_start_run closes the old run. Why: continue without redoing work.
- Memory: rank saved memories locally (memory-rank.ts) and inject the top 40; recall_memory searches the rest. No embeddings. Why: BYOK has no shared embedding key.
- MCP tool lists cache per connection+URL for 6h (mcp-cache.ts); clients open lazily on first call; recheck/failure clears the cache. Resources/prompts are read-only. Why: skip discovery latency safely.
- Discovery: classifyTask (discovery.ts) picks small/medium/large/high_risk; questions go only through ask_user → task_questions, answers only through answer_task_question (atomic, idempotent; only the call closing the last open required question returns resume). Open required questions make finalStage AWAITING_INPUT. Why: no silent guessing, no double resume.
- Suggestions (task_suggestions) are never consent; only an accepted decision changes scope. Specs are versioned rows in task_specifications.
- Reasoning: reasoning.ts maps auto/speed/balanced/deep to provider options only for adapters+models with documented support; unknown models get none. Team size and step caps come from teamPolicy/profilePolicy; dispatch is forced only for large/high-risk non-speed work. Roles route to coding/reviewer models when configured, else the master. Why: truthful capabilities, smallest effective team.
- Repo trees cache across runs per user+repo+branch keyed by head SHA (tree-cache.ts, 30 min, 50 entries). Helpers end with a fenced JSON report validated by worker-report.ts; missing reports or unowned files are surfaced to the master as contractIssues. Skill auto-matching uses measured completion rates (skill-stats.ts, ≥4 samples) only for weak keyword matches; triggers/names/always-on are unaffected.


## Customer-owned coding projects (BYO infrastructure)
- The hosted Forge platform and a customer's generated application are different systems. Lovable hosts Forge only; never assume Forge's own Supabase, GitHub, Vercel or deployment environment is the customer's project.
- At task creation, bind the selected customer GitHub account/repository/branch, Supabase account/project, Vercel account/project and AI provider/key to the task. Re-read those task-pinned IDs before every provider operation.
- Explicit account pins are authoritative. If a pinned credential is deleted, rejected, lacks permission or cannot reach its selected project, stop that provider action and request reconnection/reselection; never silently fall back to another saved account.
- Keep independent provider accounts independent. Parallel tasks may use different GitHub/Supabase/Vercel accounts; never share a token, project ref, deployment ID, branch or preview secret across tasks or users.
- Master agent owns the plan, customer intent, shared integration decisions and final acceptance. Delegate independent work in dependency waves: architect/explorer first for unfamiliar repositories; frontend/backend/database/integration coders on exclusive file paths; tester/QA and security/reviewer after integration. Use the smallest team that meets the task's risk and latency needs; avoid redundant agents and overlapping writers.
- Specialists return structured evidence: changed paths, assumptions, checks run, exact failures, provider resources touched and blockers. Only the master reconciles conflicts, verifies task ownership and decides whether another wave is needed.
- Before any remote change, distinguish read-only discovery from writes. Require the task's configured autonomy and approval for repo creation, project creation/relinking, migrations, environment writes, production deployments, destructive changes and MCP actions. A plan or recommendation is not consent.
- Connect & sync must validate the complete chain: selected GitHub repo/branch → selected Vercel project and root/build settings → selected Supabase project → framework-specific public/server environment mapping → auth redirect URLs → pending migrations/approval → exact-commit build and live route verification.
- Environment mapping is derived from the generated project's framework and actual imports. Never assume all customer projects use Next.js or Vite. Publishable keys only in browser; service-role/secret keys, provider tokens and AI API keys server-only.
- Preview lifecycle is separate: task-scoped sandbox, dependency install, dev process readiness, HTTP route probe, browser console/network capture, redacted logs and repeatable diagnosis. A server process starting is not a successful preview; a preview is not a production deployment.
- Repair in bounded root-cause rounds. Preserve customer data, RLS, auth, migrations and existing provider configuration. Never delete files to suppress errors, fake successful provider responses, disable checks or claim unverified states as healthy.
- Completion report includes exact repository/branch/commit, customer-selected provider project identifiers (non-sensitive), preview state, deployment state, tests and routes checked, approvals used and unresolved blockers.

## Forge UAF conformance
- Follow `UAF/constitution.md` and the relevant `UAF/protocols/*` documents for every substantial task. These documents augment this file; existing implementation invariants below remain authoritative where they are more specific.
- The active agent identity and visible product name are **Forge**. Do not add a separate competing agent runtime or duplicate existing lifecycle, model, memory, skill, team or control-plane services.
- General-purpose task handling must be domain-aware: coding, research, business, documents, analytics and automation each use relevant skills and appropriate verification.
- Model independence means capability discovery and normalized provider adapters; never assume a model supports tool calls, vision, JSON schema or a specific reasoning parameter.
- Tool calls require real schema validation, owner/task permissions, bounded budgets, safe retries and observed postconditions. No narration-only completion.
- Customer infrastructure sync is a resumable saga across independent provider APIs, not an atomic transaction. Re-read authoritative state after ambiguous write failures, use stable idempotency keys where supported, preserve successful steps and reject stale workers via fencing.
- Connect and Auto-fix are not consent to production changes. Migrations, production environment writes, domain/permission changes, resource creation/relinking and deploys must remain behind exact existing approval flows. Never let a broad sync option bypass the migration approval UI.
- A provider sync result must distinguish verified, pending, blocked, failed, skipped and unverified. Never state that all resources are in sync if any required step has not been checked.
- Evaluation: UAF cases are machine-readable; score reviewed observations with evaluation.ts. Critical failures, missing observations, duplicate/unknown results and forbidden actions block release regardless of score. Catalog validation is not a model evaluation.
- Training: no task/chat/customer data is collected automatically. Only explicitly consented, human-reviewed examples may enter the offline dataset prep; secrets and consent references are removed before export. LoRA training is optional, open-weight-only and requires an external CUDA GPU. Never claim the hosted model weights were trained unless an actual training run and artifact are verified.
